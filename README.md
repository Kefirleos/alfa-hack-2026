# Новостная аналитика для принятия бизнес-решений

Прототип команды GenAlpha для хакатона «Альфа-Будущее 2026».

Сервис берёт деловые новости и объясняет руководителю крупной компании, что они значат именно для его бизнеса: что произошло, чем это грозит или чем помогает, что думает по этому поводу Альфа-Банк и что стоит проверить. У каждого вывода есть источник, а модель не может сослаться на то, чего нет в данных.

Репозиторий приватный, в нём лежат данные банка и PDF-отчёты аналитики, поэтому публиковать его нельзя. Решение запускается локально через Docker, отдельного хостинга у нас нет.

## Что умеет прототип

- Лента новостей для каждой компании. Новости сортируются правилами из YAML-файлов: тема новости, признаки компании (отрасль, внешняя торговля, кредиты, платежи), роль пользователя, свежесть и надёжность источника.
- Разбор новости в виде карточки: что произошло, почему важно компании, риски, возможности, действия, позиция Альфа-Банка.
- Каждое утверждение в карточке имеет тип: факт из новости, позиция банка (пересказ отчёта аналитики со ссылкой на отчёт и его дату, номер страницы есть в ответе API), вывод ИИ или предложение продукта (помечено как реклама). Тип виден пользователю.
- Блок «Как получен вывод» показывает шаги и инструменты, которые использовал агент, а строка «Неопределённость» говорит, чего не хватает для точного вывода.
- Четыре роли: генеральный директор, финансовый директор, руководитель казначейства, главный бухгалтер. Для каждой своя расстановка акцентов.
- Чат по карточке. Отвечает только по данным разбора и найденным отчётам банка.
- Свои новости: можно отправить текст или ссылку, и сервис построит разбор для выбранной компании. Эндпоинт `POST /insights/custom`, пробовать удобно в Swagger на http://localhost:8000/docs (нужен ключ). Формы в интерфейсе пока нет.
- Прототип встроен в интерфейс Альфа-Бизнес: главная, счета, платежи, кредиты, аналитика, сравнение клиентов и раздел «Бизнес-инсайты».

## Запуск через Docker

Нужен Docker Desktop (или Docker Engine с compose v2) и около 3 ГБ места. Видеокарта не нужна.

```
git clone https://github.com/Kefirleos/alfa-hack-2026
cd alfa-hack-2026
cp .env.example .env
docker compose up --build
```

В Windows PowerShell вместо `cp` используйте `copy .env.example .env`. В файле `.env` впишите свой `LLM_API_KEY` (подробнее ниже). Без ключа тоже можно посмотреть заранее подготовленные разборы.

Первая сборка занимает несколько минут: при сборке образа из CSV строится база SQLite (около 85 тысяч компаний и 1,38 млн строк платежей).

После запуска:

- интерфейс: http://localhost:5173
- API и Swagger: http://localhost:8000/docs
- проверка состояния: http://localhost:8000/health

Остановить можно через Ctrl+C. Чтобы заодно удалить кэш разборов: `docker compose down -v`.

## Запуск без Docker

Нужен Python 3.12 или новее.

```
cd backend
python -m venv .venv
source .venv/Scripts/activate
pip install -r requirements.txt
python -m scripts.load_companies
python -m scripts.load_payments
PYTHONPATH=../frontend uvicorn ext.app_ext:app --port 8000
```

Активация окружения на других системах: в PowerShell `.venv\Scripts\Activate.ps1`, в Linux и macOS `source .venv/bin/activate`. В PowerShell переменную задают так: `$env:PYTHONPATH="../frontend"`.

Скрипт `load_companies` отрабатывает за пару секунд, `load_payments` занимает около полутора минут. Во втором терминале запустите статику:

```
cd frontend
python -m http.server 5173
```

Интерфейс откроется на http://localhost:5173. Команда `uvicorn app.main:app` поднимет только базовое API, без страниц счетов, платежей, кредитов и аналитики, они подключаются слоем `frontend/ext`.

## Настройка LLM

Всё настраивается через переменные окружения, менять код не нужно. Образец лежит в `.env.example`.

- `LLM_API_KEY` это ключ шлюза. В репозитории ключей нет, у жюри будет свой.
- `LLM_BASE_URL` по умолчанию `https://changellenge.up.railway.app/v1`. Если нет VPN и не открывается, используйте `https://api.alfahack-gateway26.ru/v1`.
- `LLM_TIMEOUT` таймаут запроса в секундах, по умолчанию 90.
- `OFFLINE_MODE=1` полностью отключает обращения к модели, остаётся только кэш.
- `LLM_MODEL_FAST`, `LLM_MODEL_WRITER`, `LLM_MODEL_CRITIC`, `LLM_MODEL_RESEARCH`, `LLM_MODEL_FALLBACK`, `LLM_MODEL_VISION` задают модели по ролям (шесть моделей, разрешённых в кейсе).
- `LLM_CACHE_DIR` папка кэша ответов модели.

Основной разбор и чат идут через `deepseek/deepseek-v4.1-flash` (роль RESEARCH), разметка новостей через `google/gemma-4-26b-a4b-it` (роль FAST). Остальные модели можно подключить сменой переменных.

Ответы модели кэшируются на диске по хэшу запроса, поэтому повторный запрос ничего не стоит. Расход токенов и время каждого вызова пишутся в `llm_cache/usage.jsonl`. Если дневной лимит шлюза исчерпан, сервис отвечает 503 и пишет об этом в интерфейсе.

Без ключа работают только заранее подготовленные разборы: для трёх демо-клиентов (U_57706, U_9250, U_88715), ролей cfo и ceo и шести главных событий ленты. Они лежат в `backend/demo_cache`. Там же ответы чата для первых двух событий каждой ленты на вопросы «Что это значит для нас?», «Что проверить в первую очередь?» и «Что по этому поводу думает банк?», а для ставки ЦБ у клиента U_9250 и роли cfo ещё на «Что банк ждёт по ставке до конца года?», «Что нам проверить по кредитам?» и «Почему банк поменял прогноз?». Регистр, буква «ё» и знак вопроса в конце не важны, остальная формулировка должна совпадать. Новые разборы, чат с другим вопросом и свои новости без ключа не работают.

## Как проверить, шаг за шагом

1. Откройте http://localhost:5173. Вход выполняется автоматически (см. «Тестовые пользователи»). В шапке выберите «Клиент 2», это U_9250, и роль «Финансовый директор».
2. Посмотрите главную и вкладки «Счета», «Платежи», «Кредиты», «Аналитика». Профиль клиента взят из CSV, а счета, платежи, кредиты, курсы и «уровень риска» смоделированы по профилю. Это демонстрация встраивания в Альфа-Бизнес, а не данные банка (в платежах и кредитах это указано прямо в строках).
3. Откройте «Бизнес-инсайты». Лента персональная: у каждого события есть тип (риск, возможность или нейтрально), важность и причина, почему его показали именно этой компании.
4. Откройте первый инсайт (ЦБ сохранил ключевую ставку на уровне 14%). Там шесть блоков. У каждого утверждения виден тип, у фактов и позиции банка источник (новость или отчёт банка с датой), у выводов ИИ признаки компании. Справа список источников, признаки компании, строка «Неопределённость» и трасса «Как получен вывод».
5. В чате задайте вопрос, например «Что банк ждёт по ставке до конца года?». Ответ придёт в виде утверждений с типами (факт, позиция банка, вывод ИИ). Источники каждого утверждения есть в ответе API (`POST /insights/{id}/chat` в Swagger), в окне чата у утверждений показываются только тип и текст.
6. Смените клиента («Клиент 1» это U_57706, оптовая торговля топливом, «Клиент 3» это U_88715, производство электрооборудования) и роль в шапке страницы, лента и формулировки изменятся. Без ключа разборы открываются для ролей «Финансовый директор» и «Генеральный директор».
7. Откройте http://localhost:8000/docs, найдите `POST /insights/custom` и отправьте, например, `{"company_id": "U_9250", "role": "cfo", "text": "Банк России повысил ключевую ставку на 1 процентный пункт, до 15% годовых."}` (нужен ключ). Примерно через минуту придёт разбор для выбранной компании, а его id можно открыть в интерфейсе: `http://localhost:5173/insight.html?id=<id из ответа>`.
8. Откройте вкладку «Сравнение»: ленты двух компаний рядом.
9. В ленте «Бизнес-инсайтов» под каждым событием есть вопрос «Полезно?» и кнопки «Да» и «Нет». Оценка сохраняется в `feedback.jsonl` в папке разборов (`backend/data/insights`, в Docker это том `insights`) и используется в метриках качества.

## Тестовые пользователи

Авторизация демонстрационная: вход выполняется автоматически под пользователем demo, пароль не проверяется. Роль выбирается списком в шапке (генеральный директор, финансовый директор, руководитель казначейства, главный бухгалтер), клиент тоже. Заранее подготовленные разборы без ключа есть для ролей «Финансовый директор» и «Генеральный директор», для остальных ролей нужен ключ. В списке клиентов показаны условные имена: «Клиент 1» это U_57706 (оптовая торговля топливом), «Клиент 2» это U_9250 (строительство инженерных сооружений), «Клиент 3» это U_88715 (производство электрооборудования).

## Данные

В проекте реальные данные хакатона: три CSV (профили компаний, платежи, связи) и 9 PDF-отчётов аналитики Альфа-Банка лежат в `backend/data/raw`. Синтетические данные не нужны, организаторы разрешили хранить реальные в приватном репозитории. Новости мы собираем из открытых RSS-лент (ЦБ, Коммерсантъ, Ведомости, Прайм, Интерфакс, Правительство), список источников в `backend/data/reference/sources.yaml`. Полный перечень сторонних материалов в файле THIRD_PARTY_NOTICES.md.

Как мы работаем с данными:

- Названий компаний в данных нет, имена условные.
- Платежи это только выборка: у демо-клиентов наблюдаемые поступления составляют 0,06-0,09% годовой выручки, а 82% суммы всех платежей в файле это переводы самому себе. Поэтому мы считаем только относительные доли без самоплатежей, а модели в промпте велим писать «по наблюдаемым платежам».
- В модель отправляются агрегированные признаки (отрасль, размер, флаги кредита, структура платежей), а не сырые строки платежей.
- Мы не используем поле NEGATIVEMARK: в кейсе оно описано как «наличие признака ключевого собственника», но из этого не следует, риск это или нет, поэтому выводов на нём не строим. Не используем также период платежей (за какой срок посчитан PAY_AMT, не указано) и данные по физлицам (связи есть только у 5% компаний).
- Текст PDF мы распознали через Tesseract один раз, результат лежит в `backend/data/processed/alfa_pages.jsonl` (64 страницы). В обычной работе OCR не запускается. Для повторного запуска нужны `backend/requirements-ocr.txt` и установленный Tesseract. Таблицы и графики распознаются хуже обычного текста.
- Счета, платежи, кредитные предложения, курсы и «уровень риска» на главной и в «Аналитике» смоделированы по профилю клиента (`frontend/ext/real_data.py` и `analytics_ext.py`). Это демонстрация встраивания в Альфа-Бизнес, а не данные банка.

## Как устроено

Новости собираются скриптом `ml/news_ingest.py`, размечаются темами (`ml/news_tagging.py`, модель gemma, а если её нет, то по ключевым словам) и сохраняются в `events.jsonl`. Из CSV строится база SQLite, из неё профиль компании со списком ограничений (что про компанию нельзя утверждать, например, что она экспортирует, если у нас есть только флаг ФТС). Отчёты банка разбиты на страницы, и по ним работает поиск BM25.

Когда пользователь открывает карточку, сервис (`ml/service.py`) сначала ищет готовый разбор в кэше. Если его нет, запускается агент (`ml/agent/loop.py`), который идёт по шагам:

1. План и сбор данных: профиль компании, поиск позиции банка по отчётам, похожие новости, продукты банка.
2. Генерация разбора моделью в виде JSON.
3. Самопроверка правилами. Нарушающие утверждения перегенерируются один раз, оставшиеся нарушения убираются. Если при этом снята вся позиция банка, вместо неё показывается ссылка на отчёт.
4. Сборка карточки с источниками и трассой.

Важная оговорка: это фиксированный конвейер (plan-and-execute). Порядок шагов и набор инструментов задаём мы, модель сама инструменты не выбирает, а строит разбор по собранным данным. Готовых агентных фреймворков мы не использовали.

Бэкенд написан на FastAPI (`backend/app` это профили, ранжирование и схемы, `backend/ml` это агент, клиент модели, поиск и кэш). Фронтенд состоит из обычных HTML и JS файлов без сборки, их отдаёт nginx. Правила вынесены в YAML (`backend/data/reference`): темы, роли и их веса, веса отраслей, продукты банка и ограничения по полям профиля.

## Безопасность и работа с ИИ

- Тексты новостей и документов считаются данными, а не командами. В промптах прямо сказано не выполнять инструкции из них.
- У агента только инструменты на чтение из заранее заданного списка. Ссылаться модель может только на метки, которые вернули инструменты (`news:`, `alfa:`, `client:`, `product:`).
- Перед показом проверяется каждое утверждение (`backend/ml/agent/checks.py`): нет ли выдуманных ссылок, есть ли у факта ссылка на новость, есть ли у позиции банка ссылка на отчёт и совпадают ли в ней числа с отчётом, опирается ли вывод на признак компании, нет ли сумм в рублях без данных пользователя и запрещённых выводов (например, что компания надёжна или ненадёжна).
- Позиция банка и мнение ИИ разделены типами утверждений, реклама помечена.
- Своя новость по ссылке скачивается только с публичных адресов: внутренние и локальные IP отклоняются, перенаправлений не больше трёх, страница не больше 500 КБ.
- Ключи читаются только из переменных окружения. Файл `.env` в `.gitignore`.
- Ограничения защиты: авторизация демонстрационная, ограничения частоты запросов нет. В промышленной версии компания и роль должны браться из токена интернет-банка, а не из запроса, каждый запрос к разбору должен проверять связь пользователя с компанией, а вызовы инструментов и модели должны писаться в журнал с пользователем и временем.

## Продуктовые метрики и мониторинг качества

Что для нас считается успехом продукта: руководитель за минуту понимает, что важно именно его компании, и верит выводу, потому что видит источник.

Метрики и текущие значения. Мы измерили их на 42 заранее построенных карточках из `backend/demo_cache` (3 клиента, роли cfo и ceo, главные события ленты).

- Покрытие источниками: доля утверждений типа «факт» и «позиция банка», у которых есть источник. Цель 100%, сейчас 100% (0 из 132 без источника).
- Доля снятых утверждений: сколько утверждений убрала самопроверка после повторной генерации. Цель не больше 5%, сейчас 1,9% (11 из 592 сгенерированных утверждений, затронуто 9 карточек из 42).
- Покрытие позицией банка: доля карточек, где блок позиции банка заполнен. Цель не меньше 70%, сейчас 69% (29 из 42, из них в 2 карточках только ссылка на отчёт). Если в отчётах по теме ничего не нашлось, разбор честно пишет, что подходящей позиции нет, а если модель ссылалась на отчёт, но самопроверка сняла её утверждения, мы показываем ссылку на сам отчёт.
- Время разбора: медиана и максимум секунд на карточку. Цель медиана до 30 с, сейчас медиана 37 с, максимум 85 с (из-за повторных генераций).
- Precision@3 и NDCG@5 ленты: насколько релевантные события попадают в топ. Считаются на экспертной разметке пар «компания и новость». Цель precision@3 не меньше 0,7. Значения будут измерены на этапе доработки.
- Доля дубликатов в топ-5 ленты (события одной темы и дня). Цель не больше 10%, сейчас 0% (0 из 30).
- Свежесть: медианный возраст показанных новостей в днях. Цель не больше 7, сейчас медиана 2 дня (максимум 4).
- Полезность: доля оценок «Полезно» среди всех оценок в ленте. Цель не меньше 70%. Оценки уже сохраняются, значения будут посчитаны, когда наберётся выборка.
- Стоимость разбора в рублях по `usage.jsonl` и ценам моделей. Цель не больше 3 рублей, сейчас один вызов основной модели стоит в среднем около 0,11 рубля, а разбор обычно занимает один или два вызова.
- Доля ответов из кэша: попадания в кэш к общему числу запросов, берётся из `usage.jsonl`.

Как мы предлагаем следить за качеством:

1. На каждом новом разборе автоматически срабатывают правила `checks.py`. Результат виден в карточке («снято утверждений: N») и в трассе.
2. Раз в неделю и после каждого изменения промптов или правил считаем метрики выше по готовым карточкам, `usage.jsonl` и сохранённым отзывам пользователей. Для этого есть скрипт: в папке `backend` команда `python -m scripts.quality_report` (ключ не нужен).
3. Для релевантности ленты собираем тестовую выборку пар «компания и новость» из открытых источников и демо-клиентов, размечаем её вручную (0, 1, 2) и считаем precision@k и NDCG после каждого изменения весов. Выборку и критерии обоснуем на защите.
4. Пороги: если покрытие источниками ниже 100%, доля снятых выше 10% или «Полезно» ниже 60%, меняем промпт или правило и не выпускаем изменение, пока метрики не вернутся в норму. Все правки идут через pull request.
5. За бюджетом следим по `/key/info` и `usage.jsonl`. Когда остаётся меньше 20%, переходим в режим только кэша (`OFFLINE_MODE=1`).
6. Отзывы из карточек используем при следующей калибровке весов в `roles.yaml` и `okved_exposure.yaml`.

Часть метрик (источники, снятые утверждения, позиция банка, время, стоимость, кэш, свежесть, дубликаты, отзывы) считается скриптом `python -m scripts.quality_report`. Метрики релевантности (precision и NDCG) требуют ручной разметки и запланированы на этап доработки.

## Ограничения

- Платежи это выборка, точных долей контрагентов у нас нет.
- Счета, платежи, кредиты, курсы и «уровень риска» в интерфейсе смоделированы.
- Агент работает по фиксированному плану, а не выбирает инструменты сам.
- Без ключа доступны только подготовленные разборы и ответы чата, остальное возвращает 503.
- В окне чата видны типы утверждений, источники ответа есть только в API.
- У роли «Главный бухгалтер» после порога значимости в ленте остаётся всего несколько событий.
- Блок позиции банка бывает пустым: если в 9 отчётах по теме новости ничего не нашлось, разбор честно пишет, что подходящей позиции нет.
- Из новостей мы берём заголовок и анонс из RSS, полные статьи не загружаем.
- Авторизация демонстрационная.
- Сервис рассчитан на крупный бизнес с выручкой от 15 млрд рублей, как в кейсе, все три демо-клиента из этого сегмента. Фильтра по выручке в API нет: разбор можно построить для любой компании из данных, чтобы проверить работу на других профилях.

- `backend/data/reference` правила и справочники YAML

- `Dockerfile`, `docker-compose.yml`, `.env.example`, `THIRD_PARTY_NOTICES.md`
